# Booking Creation Contract and Concurrency Strategy

Task: LBC-004D - Define Booking Creation Contract and Concurrency Strategy

Status: Documentation only.

This document defines the planned contract for creating a laundry booking and the concurrency strategy required before implementation. It does not implement an API endpoint, service, repository, Prisma migration, seed, or UI.

## Proposed Endpoint

```text
POST /bookings
```

The endpoint is planned as a mutation endpoint for creating one booking in one laundry room for one fixed 2-hour slot.

The existing availability endpoint remains read-only:

```text
GET /laundry-rooms/:laundryRoomId/availability?date=YYYY-MM-DD
```

Availability reads help clients present possible slots, but they do not reserve time and do not protect the write path from concurrent requests.

## Request Body

```json
{
  "residentId": "uuid",
  "laundryRoomId": "uuid",
  "date": "YYYY-MM-DD",
  "slotStart": "HH:mm"
}
```

Field rules:

- `residentId` must be a valid UUID for an existing Resident.
- `laundryRoomId` must be a valid UUID for an existing LaundryRoom.
- `date` must be a strict calendar date in `YYYY-MM-DD` format.
- `slotStart` must be a strict local time in `HH:mm` format.
- `slotStart` must align to the fixed 2-hour slot grid.
- The initial slot grid is `00:00`, `02:00`, `04:00`, `06:00`, `08:00`, `10:00`, `12:00`, `14:00`, `16:00`, `18:00`, `20:00`, and `22:00`.

The request does not accept client-supplied `startTime`, `endTime`, or status. Those values are derived by the API.

## Timezone Decision

The API must interpret `date` and `slotStart` in the operational timezone:

```text
Europe/Stockholm
```

The API must convert the selected local slot into UTC timestamps before storing or comparing:

- `startTime`: UTC timestamp derived from `date` plus `slotStart`.
- `endTime`: UTC timestamp derived from the local slot end after the fixed 2-hour slot.

The success response must return `startTime` and `endTime` as ISO UTC timestamps and must also include:

```json
{
  "timezone": "Europe/Stockholm"
}
```

Future implementation must use the same timezone interpretation as the availability endpoint so that a slot displayed as available is evaluated consistently when the user submits the booking request.

## Success Response

HTTP status:

```text
201 Created
```

Response body:

```json
{
  "id": "uuid",
  "residentId": "uuid",
  "laundryRoomId": "uuid",
  "startTime": "2026-05-15T06:00:00.000Z",
  "endTime": "2026-05-15T08:00:00.000Z",
  "status": "ACTIVE",
  "timezone": "Europe/Stockholm"
}
```

Response rules:

- `id` is generated by the server.
- `status` is always `ACTIVE` on successful creation.
- `startTime` and `endTime` are ISO UTC timestamps.
- `timezone` records the interpretation used for the submitted `date` and `slotStart`.

## Error Contract

The endpoint should use clear `400`, `404`, and `409` responses.

### 400 Bad Request

Use `400` when the request cannot be interpreted or violates basic request rules:

- Missing body.
- Invalid JSON body.
- Missing required field.
- Invalid UUID format for `residentId`.
- Invalid UUID format for `laundryRoomId`.
- Invalid `date` format.
- Invalid `slotStart` format.
- `slotStart` is outside the fixed 2-hour grid.
- The requested slot is outside the allowed 14-day booking window.
- The requested slot is in the past.
- The derived slot is not exactly one fixed booking slot for the local booking grid.

Candidate response shape:

```json
{
  "error": "BAD_REQUEST",
  "message": "slotStart must align to the 2-hour slot grid"
}
```

### 404 Not Found

Use `404` when an identified resource does not exist:

- Resident does not exist.
- LaundryRoom does not exist.

Candidate response shape:

```json
{
  "error": "NOT_FOUND",
  "message": "Laundry room not found"
}
```

### 409 Conflict

Use `409` when the request is valid but cannot be accepted because of current domain state:

- Resident exists but is not `ACTIVE`.
- LaundryRoom exists but is not `ACTIVE`.
- The requested slot overlaps an `ACTIVE` Booking in the same LaundryRoom.
- The requested slot overlaps a BlockedSlot in the same LaundryRoom.
- The Resident already has a future `ACTIVE` Booking.

Candidate response shape:

```json
{
  "error": "CONFLICT",
  "message": "Requested slot is no longer available"
}
```

The one-future-booking rule is approved for the MVP and should be enforced with `409` when a Resident already has another future `ACTIVE` Booking.

## Domain Validation Rules

The booking creation implementation must enforce these rules before creating a Booking:

- Resident must exist.
- Resident must be `ACTIVE`.
- LaundryRoom must exist.
- LaundryRoom must be `ACTIVE`.
- Requested slot must be inside the allowed 14-day booking window.
- Requested slot must not be in the past.
- Requested slot must align to the fixed 2-hour local slot grid.
- Requested slot must not overlap an `ACTIVE` Booking in the same LaundryRoom.
- Requested slot may overlap a `CANCELED` Booking because `CANCELED` bookings remain historical and do not block availability.
- Requested slot must not overlap a BlockedSlot in the same LaundryRoom.
- Resident must not already have another future `ACTIVE` Booking.

Conflict overlap uses the existing domain rule:

```text
existing.startTime < requested.endTime
AND existing.endTime > requested.startTime
```

The overlap check is scoped to the same LaundryRoom for Booking and BlockedSlot availability conflicts.

## Concurrency Strategy

The read-only availability endpoint does not protect booking creation. Two users may read the same slot as available and submit two booking requests at nearly the same time.

The future booking creation endpoint must protect two independent conflicts:

- LaundryRoom availability: two requests must not create overlapping `ACTIVE` Bookings for the same LaundryRoom slot.
- Resident limit: two requests must not create two future `ACTIVE` Bookings for the same Resident, even when the requested LaundryRooms are different.

The recommended initial implementation is:

1. Start a database transaction.
2. Acquire PostgreSQL advisory locks for both `residentId` and `laundryRoomId`.
3. Use separate lock namespaces for Resident locks and LaundryRoom locks so the same UUID value cannot collide across entity types.
4. Acquire locks in deterministic order to reduce deadlock risk. The required order is Resident lock first, then LaundryRoom lock.
5. Inside the transaction, load and validate the LaundryRoom.
6. Inside the transaction, load and validate the Resident.
7. Inside the transaction, check for overlapping `ACTIVE` Booking records in the same LaundryRoom.
8. Inside the transaction, check for overlapping BlockedSlot records in the same LaundryRoom.
9. Inside the transaction, check whether the Resident already has a future `ACTIVE` Booking.
10. Create the Booking only if every validation passes.
11. Commit the transaction.

The LaundryRoom advisory lock must be derived deterministically from `laundryRoomId` and the LaundryRoom lock namespace so concurrent booking attempts for the same LaundryRoom serialize through the availability critical section.

The Resident advisory lock must be derived deterministically from `residentId` and the Resident lock namespace so concurrent booking attempts by the same Resident serialize through the one-future-booking critical section, including attempts across different LaundryRooms.

Booking attempts for different Residents and different LaundryRooms may proceed independently. Booking attempts that share either the same Resident or the same LaundryRoom must serialize.

This strategy is still application-level protection. A future hardening task may add PostgreSQL exclusion constraints or another database-level range constraint strategy to protect against overlap even if application code changes.

No migration, schema change, or database constraint is created by LBC-004D.
